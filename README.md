把中文合同审查的判断标准写成可加载、可生成、可核验的工具：三观四步的分层框架、15 类常见合同的审查清单与条款标准、一份能对着正文跑的速检脚本、一套市场基准区间，以及一个逐条核对过条号的现行法条库。

同时以 [Agent Skill](SKILL.md) 形态分发：`npx skills add` 一行装上，在 Claude Code、Codex、Cursor 等工具里直接用。

## 为什么做这个

合同审查的失误很少来自「不懂法」，多数来自「漏了」。四类失误最常见：

第一类是**层次错位**。上手就改违约金比例的写法，却没发现交易结构本身触碰了强制性规定，条款改得再细也救不回来。审查应当先看交易能不能做，再看合同能不能生效，最后才逐条抠文字。

第二类是**整类条款缺失**。合同写了争议解决，却漏了通知与送达；写了保密，却没约定合同终止后是否延续。这类漏项不影响合同成立，但会在争议发生时让当事人陷入被动。

第三类是**条号记错**。违约金调减的量化标准在司法解释第六十五条，格式条款的认定要件在民法典第四百九十六条第一款，名实不符的认定规则在司法解释第十五条。这些条号靠记忆写，迟早出错；一旦写进意见书，专业性就打了折扣。

第四类是**立场没定**。同一条款对甲方是优势、对乙方就是风险。责任上限写低，卖方觉得省事、买方觉得要命。不先定立场就下结论，结论必然摇摆。

这个仓库针对这四点，给出四件东西：一份分层可勾选的清单（可按甲方或乙方切换视角）、一个照着清单跑的速检脚本、一套市场基准区间，以及一个把法条引用变成白名单的校验机制。

## 用法

```bash
# 列出全部合同类型
crc list

# 查看某类型的定位与法条依据
crc show --type sales

# 生成一份可勾选的空白审查清单（Markdown 或离线 HTML）
crc checklist --type sales --out 买卖合同审查清单.md
crc checklist --type sales --party 乙方 --format html --out 审查清单.html

# 对照清单速检一份合同正文
crc audit --type sales --file 合同.md
crc audit --type sales --file 合同.md --party 乙方 --format html --out 速检报告.html
crc audit --type sales --file 合同.md --format json

# 查看市场基准区间，或某一项的完整阈值
crc bench
crc bench --key penalty-ratio

# 查看法条库，或某一条的原文
crc laws
crc laws --key 民法典第585条

# 校验全部数据文件的结构与法条引用
crc verify
```

`audit` 做三件事：对照条款标准看哪些必备条款没有出现，扫描风险信号词，以及把量化条款与市场基准区间比对。它只做提醒不判分：关键词没命中的条款可能只是换了表述，命中也不等于条款写得没问题。它的用处是把「整类条款漏写」这种低级失误挡在交付之前。退出码 0 为未见硬伤，1 为存在待处理项。

以 `examples/contract_sample.md` 为例，这份示例合同刻意留了缺口，按乙方立场速检的结果是：

```

  - 保密条款
```

Python API：

```python
from crc import audit, compose, load_laws, render_checklist_html, verify_references

print(render_checklist_html(compose("lease", "乙方")))   # 一份乙方视角的 HTML 可勾选清单
result = audit("sales", open("合同.md", encoding="utf-8").read(), party="乙方")
print(result["missing_required"])
print(result["benchmarks"])                              # 偏离基准区间的量化条款
print(verify_references(["民法典第585条"]))                # 校验引用是否在核验库内
print(load_laws()["民法典第496条"]["text"])                # 取回条文原文
```

## 三观四步与立场

审查分四步走，前三步对应宏观、中观、微观三个层次：

| 步骤 | 层次 | 要回答的问题 |
| --- | --- | --- |
| 定立场 | — | 我代表哪一方？市场地位如何？必守项与可谈项是什么？ |
| 宏观 | 交易结构 | 这笔交易本身能不能做、由谁做、要不要批？ |
| 中观 | 合同形式 | 这份合同能不能生效、好不好用？ |
| 微观 | 条款文本 | 每一条写得对不对、全不全、能不能执行？ |

立场不是装饰。指定 `--party` 后，同一条审查项会给出不同的提示，风险等级也可能翻转。例如「损失赔偿范围是否排除间接损失」，中立口径是重要风险；站到乙方，它升级为致命风险。再如保证方式未明确，对债权人（甲方）是致命，对保证人（乙方）反而只是重要。

风险分四级：致命、重要、一般、提示。

## 数据文件

```
crc/data/
  dimensions.yaml         三观四步审查框架、风险四级定义与审查纪律
  laws.yaml               经核验的法条库（引用白名单）
  benchmarks.yaml         市场基准区间与法律上限的参照值
  contracts/
    common.yaml           通用审查项与通用条款标准
    sales.yaml            买卖合同专属审查项与条款标准
    ...                   其余合同类型
```

每份合同类型的 YAML 包含三部分：

- `checks.macro` / `checks.meso` / `checks.micro`：三个层次的审查项，每项带风险等级与法条依据，可选带 `party_notes`（按立场的提示）与 `risk_by_party`（按立场的风险等级）；
- `clauses`：条款标准，列出必备要素、常见问题与关键词（关键词用于速检匹配），多数附带 `redline` 建议文本；
- `red_flags`：风险信号词及其说明。

## 法条核验

`crc/data/laws.yaml` 是唯一合法的引用来源。清单里每一处 `basis` 都必须以 key 的形式出现在这个文件中，否则 `crc verify` 会报错，单元测试也会失败。

条文原文通过法律数据库按「法规名称 + 条号」逐条调取，返回结果均带现行有效标记，核验日期记录在文件头部。当前收录 63 条，覆盖民法典总则与合同编、典型合同分编、民法典合同编通则司法解释、劳动合同法与公司法（2023 修订）。

这样做的意义在于：意见书里写下的每一个条号，都是查过的，不是想起来的。同时也便于日后维护，法律修订时只需更新这一个文件，引用错误会立刻在测试中暴露。

一个实际的例子：合同编通则司法解释中，认定合同性质应以内容而非名称为准的规则在**第十五条**，而第十四条处理的是同一交易订立多份合同与虚假意思表示。两者常被混用，本仓库以调取的原文为准。

## 市场基准区间

`crc/data/benchmarks.yaml` 收录 9 项量化条款的参照区间：违约金比例、质量保证期、检验与验收期、付款账期、自动续约的提前通知期、竞业限制期限、保密期限、租赁期限、借款年利率。

**它与法条库性质不同，必须分清：**

- `laws.yaml` 是法律规定，条号与原文一一对应，引用错误是硬错误；
- `benchmarks.yaml` 是市场惯例区间与法律硬性上限的参照值，**不是法律规定**，只用于发现明显离谱的条款，不得当作谈判依据或裁判标准写进对外文件。

标注 `legal_limit` 的项（竞业限制二年、租赁期限二十年）是法律上限，超出部分不发生效力；其余为惯例参照，偏离只提示复核。扫描时按最不利取值判断，属保守口径，结论须人工复核。

## HTML 产物

`--format html` 生成的清单与报告均为单文件自包含：内联 CSS 与 JS，不引用任何外部资源，双击即可离线打开。清单带勾选框与核对进度条，报告带覆盖率指标卡、三级证据表格、风险清单与基准比对表。CI 中有一步专门校验产物不含 `http://` 与 `https://` 引用。

## 方法论出处

分层框架借鉴了《合同起草审查指南：三观四步法》（何力、常金光）的宏观、中观、微观分层思路，并改写为面向审查场景的四步：定立场、宏观审查、中观审查、微观条款审查。

法条依据一律以现行有效的《中华人民共和国民法典》（2021 年 1 月 1 日施行）、《最高人民法院关于适用〈中华人民共和国民法典〉合同编通则若干问题的解释》（法释〔2023〕13 号）、《中华人民共和国劳动合同法》（2012 修正）与《中华人民共和国公司法》（2023 修订）为准。

基准区间取自中国内地民商事交易的常见做法与上述法律中的硬性上限，属惯例参照，不构成法律意见。
