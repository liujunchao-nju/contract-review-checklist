# contract-review-checklist

[![tests](https://github.com/liujunchao-nju/contract-review-checklist/actions/workflows/tests.yml/badge.svg)](https://github.com/liujunchao-nju/contract-review-checklist/actions/workflows/tests.yml)
[![License: MIT](https://img.shields.io/badge/license-MIT-blue.svg)](LICENSE)

把中文合同审查的判断标准写成可加载、可生成、可核验的工具：三观四步的分层框架、八类常见合同的审查清单与条款标准、一份能对着正文跑的速检脚本，以及一个逐条核对过条号的现行法条库。

## 为什么做这个

合同审查的失误很少来自「不懂法」，多数来自「漏了」。三类失误最常见：

第一类是**层次错位**。上手就改违约金比例的写法，却没发现交易结构本身触碰了强制性规定，条款改得再细也救不回来。审查应当先看交易能不能做，再看合同能不能生效，最后才逐条抠文字。

第二类是**整类条款缺失**。合同写了争议解决，却漏了通知与送达；写了保密，却没约定合同终止后是否延续。这类漏项不影响合同成立，但会在争议发生时让当事人陷入被动。

第三类是**条号记错**。违约金调减的量化标准在司法解释第六十五条，格式条款的认定要件在民法典第四百九十六条第一款，名实不符的认定规则在司法解释第十五条。这些条号靠记忆写，迟早出错；一旦写进意见书，专业性就打了折扣。

这个仓库针对这三点，给出三件东西：一份分层可勾选的清单、一个照着清单跑的速检脚本、一个把法条引用变成白名单的校验机制。

## 用法

```bash
# 列出全部合同类型
crc list

# 查看某类型的定位与法条依据
crc show --type sales

# 生成一份可勾选的空白审查清单
crc checklist --type sales --out 买卖合同审查清单.md

# 对照清单速检一份合同正文
crc audit --type sales --file 合同.md

# 输出 Markdown 报告
crc audit --type sales --file 合同.md --markdown --out 速检报告.md

# 查看法条库，或某一条的原文
crc laws
crc laws --key 民法典第585条

# 校验全部数据文件的结构与法条引用
crc verify
```

`audit` 做两件事：对照条款标准看哪些必备条款没有出现，以及扫描风险信号词。它只做提醒不判分，关键词没命中的条款可能只是换了表述，命中也不等于条款写得没问题。它的用处是把「整类条款漏写」这种低级失误挡在交付之前。

以 `examples/contract_sample.md` 为例，这份示例合同刻意留了缺口，速检结果是：

```
合同类型：买卖合同（sales）
条款标准：10 项，命中 5 项，覆盖率 50.0%

必备条款未见（5 项）：
  - 争议解决条款
  - 保密条款
  - 不可抗力条款
  - 通知与送达条款
  - 所有权与风险转移条款

风险信号（2 处）：
  - [重要] 最终解释权条款（命中：最终解释权、最终解释、解释权归）
      由一方单方保留解释权，属于加重对方责任、排除对方主要权利的格式条款，可能不成为合同内容。
  - [重要] 违约金畸高（命中：按合同总额的百分之五十、合同总额的百分之五十）
      明显超出可预见损失的违约金，对方可请求调减，超过损失百分之三十的一般会被认定过高。
```

Python API：

```python
from crc import audit, compose, load_laws, render_checklist, verify_references

print(render_checklist(compose("lease")))          # 一份租赁合同审查清单
print(audit("sales", open("合同.md", encoding="utf-8").read())["missing_required"])
print(verify_references(["民法典第585条"]))         # 校验引用是否在核验库内
print(load_laws()["民法典第496条"]["text"])         # 取回条文原文
```

## 支持的合同类型

| 类型标识 | 名称 | 分类 |
| --- | --- | --- |
| `common` | 通用审查项 | 基础 |
| `sales` | 买卖合同 | 物权类 |
| `lease` | 租赁合同 | 物权类 |
| `service` | 承揽与服务合同 | 服务类 |
| `loan` | 借款合同 | 金融类 |
| `labor` | 劳动合同 | 劳动类 |
| `equity` | 股权转让合同 | 公司类 |
| `tech` | 技术开发合同 | 技术类 |
| `construction` | 建设工程合同 | 建设工程 |

生成清单时，通用审查项会与该类型的专属项合并，通用项在前。新增一个合同类型不需要改代码，在 `crc/data/contracts/` 下加一个 YAML 文件即可。

## 数据文件

```
crc/data/
  dimensions.yaml         三观四步审查框架、风险四级定义与审查纪律
  laws.yaml               经核验的法条库（引用白名单）
  contracts/
    common.yaml           通用审查项与通用条款标准
    sales.yaml            买卖合同专属审查项与条款标准
    ...                   其余合同类型
```

每份合同类型的 YAML 包含三部分：

- `checks.macro` / `checks.meso` / `checks.micro`：三个层次的审查项，每项带风险等级与法条依据；
- `clauses`：条款标准，列出必备要素、常见问题与关键词（关键词用于速检匹配）；
- `red_flags`：风险信号词及其说明。

风险分四级：致命、重要、一般、提示。定级以审查立场为前提，同一条款对甲方是优势、对乙方就是风险。

## 法条核验

`crc/data/laws.yaml` 是唯一合法的引用来源。清单里每一处 `basis` 都必须以 key 的形式出现在这个文件中，否则 `crc verify` 会报错，单元测试也会失败。

条文原文通过法律数据库按「法规名称 + 条号」逐条调取，返回结果均带现行有效标记，核验日期记录在文件头部。当前收录 52 条，覆盖民法典合同编与总则、民法典合同编通则司法解释、劳动合同法与公司法（2023 修订）。

这样做的意义在于：意见书里写下的每一个条号，都是查过的，不是想起来的。同时也便于日后维护，法律修订时只需更新这一个文件，引用错误会立刻在测试中暴露。

一个实际的例子：合同编通则司法解释中，认定合同性质应以内容而非名称为准的规则在**第十五条**，而第十四条处理的是同一交易订立多份合同与虚假意思表示。两者常被混用，本仓库以调取的原文为准。

## 方法论出处

分层框架借鉴了《合同起草审查指南：三观四步法》（何力、常金光）的宏观、中观、微观分层思路，并改写为面向审查场景的四步：定立场、宏观审查、中观审查、微观条款审查。

法条依据一律以现行有效的《中华人民共和国民法典》（2021 年 1 月 1 日施行）、《最高人民法院关于适用〈中华人民共和国民法典〉合同编通则若干问题的解释》（法释〔2023〕13 号）、《中华人民共和国劳动合同法》（2012 修正）与《中华人民共和国公司法》（2023 修订）为准。
